# Menus and action triggers

## Tooltip and Toggletip

Use Tooltip for brief noninteractive context on hover or focus, Toggletip for activated supplemental content with optional controls, and a visible helper or suitable task container for essential instructions/required input. Do not hide required password rules in a disappearing tip. Reuse a component's integrated tooltip instead of layering a second wrapper; website guidance that tooltips are embedded does not mean the exported Tooltip cannot support a custom trigger. Do not place links/buttons inside tooltip content.

### Tooltip naming and interaction

A control's function must have an accessible name even when its popup is hidden. Distinguish a name from extra description. Inspected `@carbon/react@1.117.0` Tooltip clones exactly one child: label establishes aria-labelledby unless the child already supplies it; description establishes aria-describedby unless the child already supplies it. Label wins when both are supplied. A label can replace an existing visible-text name; prefer description for supplementary context and inspect combined naming. Existing relationships are preserved rather than automatically concatenated. Custom children must forward these props and events to their focusable DOM target.

- Keyboard focus opens immediately; hover defaults to a 100ms entrance and 300ms leave delay. Mouse-focus and drag handling differ from keyboard focus. Moving onto the content is intended to retain hover availability; test the trigger/content gap and delayed-state cancellation. Escape closes and retains trigger focus; document-level Escape handling also runs while open, so test nested dialogs and multiple instances. closeOnActivation defaults false and optionally closes on click/Enter/Space without replacing the trigger's action.
- Tooltip content has role=tooltip, with aria-hidden=false when open and true when closed, contrary to Accessibility's unconditional aria-hidden=true shorthand. Its noninteractive-content hook is present, but the inspected tooltipRef is not visibly attached to rendered content: do not rely on a development warning as enforcement. Render only suitable text regardless.
- DefinitionTooltip is a separate native button with aria-controls/describedby/expanded, default bottom alignment and optional openOnHover. Focus opens it; primary mousedown and Enter/Space toggle it, blur/mouseleave close, and focused Escape closes. This conflicts with prose saying its trigger only takes focus/hover and is otherwise noninteractive. Check focus-plus-click event order, touch, persistent reading and full term naming rather than copying an inert span. tooltipText is deprecated in favor of definition; native title is not a substitute for keyboard/touch access to a truncated term.
- Generic Tooltip defaults align=top, and Popover defaults autoAlign=false; neither proves website claims of automatic edge detection. DefinitionTooltip explicitly passes autoAlign. Tooltip passes other Popover props through. Verify collision flipping, clipping, scrolling containers, portals, mobile and RTL; a design rule for bottom placement on mobile requires application/version-specific verification, not an assumed automatic breakpoint.

Documented geometry: multiline max-width 288px/padding 16px; compact single-line max-width 208px, horizontal padding 16px and vertical 2px; definition max-width 176px, horizontal padding 16px and vertical 8px. Tooltip gap is 4px and caret 6px. Use inverse background/text and semantic focus/interactive borders; definition trigger has a dotted underline. Labels use label-01 and body uses body-01. Fit translated content without horizontal clipping or obstructing relevant content. A one/two-word naming recommendation does not excuse an ambiguous label.

### Toggletip state and focus

Toggletip opens on native trigger Enter/Space or pointer activation, remains available until dismissal, and allows ordinary controls in page tab order rather than a modal focus trap. Opening should leave focus on the trigger; Tab enters content, exits after the last control, and text-only content advances to the next page stop. Escape dismisses and returns focus to the invoker when focus was within the popup. Specify reverse traversal, outside dismissal and state/recovery of quick edits; avoid putting an essential workflow solely inside the tip.

Inspected Toggletip owns local state initialized with defaultOpen; no explicit controlled-open callback contract is defined in its own props. It passes rest to Popover after internal props, so overriding open/onBlur/onKeyDown can diverge from context or replace coordination rather than creating a supported controlled mode. Default ToggletipButton supplies aria-expanded/controls, a translated label and an open-content description. Its non-button as branch forwards click only, omits the normal ARIA coordination/ref, and leaves keyboard semantics to that custom component. Rest can override generated button handlers/relationships: compose deliberately.

Escape handling checks the first direct wrapper child for an HTMLButtonElement before restoring focus. Wrappers/custom triggers can break restoration. Blur closes when relatedTarget leaves, but null relatedTarget is deliberately ignored while open; window blur and capture-phase outside pointerdown/mousedown also dismiss, including composed-path checks. These are source receipts, not proof for portaled child controls, nested dialogs or focus traversal. ToggletipContent forwards className, generated ID, children and ref; arbitrary props are not spread onto PopoverContent. ToggletipActions arranges actions but does not save, close, validate or restore focus automatically.

Documented Toggletip max-width is 288px/four columns, padding 16px, gap 8px, icon 16px with 8px adjacent spacing, body-01 and inverse text/background. A constrained scrolling-body/fixed-footer example is a pattern, not a built-in component feature. autoAlign is passed through and not defaulted true; test the 16px page-edge intent and documented mobile-below placement. Long content may need a larger container. Do not copy Popover's 352px generic recommendation into every Toggletip.

## Popover is a container, with a composed interaction

Popover supplies a floating visual foundation for tooltip, menu and disclosure families; it does not make their roles or keyboard contracts interchangeable. Use commands as menus, data choices as dropdowns and ordinary form controls in a disclosure. Choose the supported higher-level component when it owns the required behavior.

Public Popover click-trigger guidance keeps focus on the trigger after Enter/Space toggles open; Tab enters interactive content, last Tab closes and advances, and text-only content closes on Tab to the next control. Escape dismisses. This differs from generic disclosure guidance that moves focus immediately to the first control. Follow the selected composition, expose its trigger name/expanded relationship, and test both directions. Interactive content needs click/touch/keyboard access; do not make hover its sole entry route. Keep hover/focus help available while users move into it when the selected help pattern requires that behavior.

Style guidance uses a 352px/four-column recommended maximum, 16px padding, contextual layer/inverse roles and normally 2px corners. Caret/no-tip variants have a documented 4px gap; tab-tip attaches flush to its toolbar/header with square corners. Caret alignment relates to the trigger. Bound vertical content without horizontal overflow, preserve usable fixed actions/header where needed, and choose a different task container when the interaction outgrows a small popover. Avoid nested popovers; the Usage exception allows tooltips within content, which still need clipping and keyboard checks. These measurements describe the documented variant, not a universal override across release flags.

Selected installed `@carbon/react@1.117.0` declarations/source were inspected:

- `open` is controlled. `onRequestClose` must actually update that state; the component cannot dismiss a permanently true prop. Supply trigger toggle/ARIA behavior as part of the composition.
- `autoAlign` defaults to false despite Usage's general automatic-placement statement. Code describes Autoalign as experimental. `autoAlignBoundary` controls its calculation boundary; dynamic-floating-style flags can use floating positioning without enabling collision flipping. Verify actual edge/portal/scroll-container behavior instead of assuming every floating variant automatically fits.
- Its Escape handler only acts when the event target is in that popover content and the event is not already prevented. It requests closing and focuses the first tabbable element in the wrapper, which must be the intended invoker in the composition. Outside click and focusout request closing, with special DatePicker handling. Test real nested/portaled content and trigger-focused Escape rather than treating this source as a complete generic dialog implementation.
- `enable-v12-release` suppresses the caret and changes tab-tip offset; `caret` is deprecated. Alignment declarations prefer top/bottom/left/right with start/end; older corner names are deprecated. Do not apply current website geometry blindly across these flag states.

Verify trigger toggle/name/state, focus entry/return, Tab/Shift+Tab/Escape/outside dismissal, hover/touch behavior, content roles, controlled closing, nested portals, clipping and responsive/RTL placement. Source/API inspection is not runtime proof.

## Choose the task boundary

Menus expose commands for a selected object/context. Use a dropdown/select for choosing form data and a popover for complex input groups. Keep essential frequent actions discoverable outside overflow when possible. Provide a keyboard/touch route to context actions instead of relying exclusively on right-click.

A menu button groups peers; a combo button executes its frequent default with a separate trigger for alternatives; overflow suits contextual row/card actions. Name repeated icon triggers with their object context. A combo's main action must not merely open the alternatives. Default action and trigger are separate tab stops; Escape returns to the trigger that opened the menu.

Menu-button variants are primary/tertiary/ghost; combo is primary and overflow is ghost. Public guidance suggests fewer than five menu-button options and at most twelve context/overflow options, with shallow submenus and meaningful grouping. These are scanning targets, not reasons to discard necessary actions or silently change task scope.

## State, focus and behavior

- Opening puts focus in the menu; Up/Down moves between items. Enter/Space invokes the focused command; submenu keys and Escape manage the current menu level. Follow the installed implementation's RTL key behavior and test it, rather than assuming mirrored artwork implements mirrored keyboard logic.
- Tab exits a command menu rather than walking each command. Settings popovers with ordinary form controls use Tab through those controls. Never apply a command-menu role to a mixed form solely because both float above content.
- Give menus and triggers names and expanded relationships. Commands use menuitem, independently checked items menuitemcheckbox, and mutually exclusive choices menuitemradio with checked state. The radio-item role belongs to each item, not the group container. Separators do not take focus. Disabled command focus behavior differs from a native disabled button; inspect the selected component rather than globally removing all disabled menu items from arrow traversal.
- Persistent selected options must remain coherent after closing/reopening. Activation focus depends on the outcome: a dialog needs its dialog focus contract; ordinary dismissal returns to the invoker; removal of that invoker needs a deliberate successor. Clicking outside and Escape must not commit an unchosen command.
- Displayed shortcut text is only a hint unless the application registers that shortcut. Use platform-appropriate labels and test actual dispatch without interfering with browser/OS shortcuts.

## Geometry and labels

Menu rows are documented at 24/32/40/48px and normally match their trigger. Width guidance is 160–288px, with longer/fluid trigger alignment exceptions; ghost triggers retain compact label/caret geometry. Reserve consistent checkmark space for selected and unselected items. Position against available space, container clipping and RTL; do not let a nominal minimum width overflow a narrow viewport.

Use body-compact-01, contextual layer/hover/border roles and component-specific danger/focus styling. Preserve full accessible item names and keyboard/touch access to truncated meaning; a browser title tooltip alone is insufficient. A danger hover fill does not implement destructive-action recovery or confirmation.

## Resolve documentation and API differences

- Menu Usage says extra-small buttons are unsupported, while Menu buttons Usage/Style list them. Installed 1.117.0 MenuButton and ComboButton declarations accept `size="xs"`. This settles the API question for that release only; actual rendered size/hit area still needs verification.
- Menu accessibility prose assigns menuitemradio to "radio groups". Installed MenuItemRadioGroup uses a group container and individual menuitemradio children, consistent with the [APG menu pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/). Do not reproduce the ambiguous prose as incorrect markup.
- Menu-button accessibility describes `iconDescription` for combo translation. Installed 1.117.0 ComboButton declares `translateWithId`, with the key `carbon.combo-button.additional-actions`; do not invent the documented old prop. Translate the meaningful Additional actions label and verify its tooltip/name.
- Installed MenuItem's `shortcut` declaration explicitly says it renders a hint without registering the shortcut. MenuItemSelectable exposes controlled `selected`/`onChange`; MenuItemRadioGroup exposes `items`, `selectedItem`, `onChange` and `itemToString`. Keep controlled selection tied to application state.
- OverflowMenu's installed entrypoint switches implementations with `enable-v12-overflowmenu`; public Code describes improved APG behavior and new Menu primitives under that flag. Inspect the actual active flag/export/children contract and migration effects before enabling it. A future-v12 statement or unchanged appearance does not prove identical keyboard behavior.
- Several Related Popover links incorrectly point to Dropdown. Follow the real [Popover documentation](https://carbondesignsystem.com/components/popover/usage/) rather than inferring the components are interchangeable.

Verify names/context, open/close/outside click, focus return/removal, arrows/Enter/Space/Tab/Escape, submenu direction, checked/disabled state, shortcut execution, actual action outcomes, portal clipping, long labels, responsive widths and theme/focus contrast. Installed-source inspection is not a practical pass.

## Separate legacy Overflow menu guidance

The standalone Overflow menu four-tab text was also reviewed. It places consequential actions below a divider, uses32/40/48px trigger/item sizes and describes left/right placement to keep the menu visible. These principles supplement contextual action naming and recovery; a divider alone is not a safety mechanism.

Its Style table specifies a0.3-opacity shadow and button-danger-primary hover, while newer Menu specifies0.2-opacity shadow and support-error hover. Do not combine both tables into a new global component skin. Resolve against the actual active OverflowMenu implementation and semantic tokens. Standalone Code lists broader framework availability, while new Menu buttons Code lists several coming-soon implementations: verify the specific framework and variant rather than treating those pages as interchangeable support matrices.
