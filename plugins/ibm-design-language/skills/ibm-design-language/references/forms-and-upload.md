# Form composition and file upload

## Text input and TextArea

Use TextInput for a single freeform value and TextArea for multiline prose. Use Select/radio choices when values come from a predefined set. Keep a persistent label; placeholder is an optional example, not the accessible name or the only place for required instructions. Hidden visual labels still need meaningful programmatic names. Keep interactive help outside the label; inspected components explicitly reject interactive label content.

- Default fields place label/helper outside; fluid fields attach flush to their containing layout with labels inside a documented 64px field. Default hanging alignment restrictions do not cancel the expressly documented fluid hanging alignment. Match the variant and context rather than copying conflicting generic examples.
- Default single-line sizes are 32/40/48px. Documented padding is 16px, label gap 8px and helper gap 4px; labels use label-01, values body-compact-01 and helper text helper-text-01. Focus/error borders are 2px with a 1px bottom rule at rest. Fluid errors can increase height. Let translated errors wrap and preserve layout relationships instead of enforcing these as clipping dimensions.
- Preserve native text editing, selection, cursor movement, paste and composition. Read-only text can remain selectable/copyable; disabled is a different state and must not be assumed universally absent from assistive-technology reading. Accessibility prose claims single-line contents select on focus, but inspected TextInput has no automatic select/focus handler. Do not introduce select-all or destructive replacement merely to imitate that prose.
- Distinguish required/native constraints, domain rules and server rejection. Invalid/warning text must identify the problem and recovery and be associated with the actual input. When helper text is replaced, retain essential format instructions in an available associated place. Sentence-case guidance concerns interface copy, not silently normalizing user values.
- TextArea documentation permits vertical resizing, a 40px minimum and content scrolling. Actual source defaults rows to four, fills its wrapper, and disables resizing when cols is supplied. Verify CSS and composition before promising resizing; choose width based on expected input and preserve long-content editing at zoom.
- A counter must specify its counting unit, limit and input policy. Character counts in inspected TextInput/TextArea use JavaScript string length and native maxLength when enableCounter is enabled; they are not grapheme counts. TextArea counterMode defaults to character; word mode uses Unicode letter-run matches, not language-aware word segmentation. Do not advertise a universal linguistic word limit.

Selected `@carbon/react@1.117.0` source inspected: TextInput's enableCounter/maxCount sets maxLength and renders a count only with a truthy maxCount. TextArea word mode prevents Space/Enter at the current limit, but its onChange can still count above the limit. Over-limit paste reconstructs existing plus pasted letter matches, joins them with spaces and assigns the DOM value; it does not account for selected-text replacement in that branch and does not explicitly dispatch the normal onChange there. This can alter punctuation/format and diverge from controlled state. Treat word enforcement as a behavior to test or compose deliberately, not reliable backend validation. Test paste into selections, punctuation/numbers, Unicode, IME, deletion, controlled rerenders and programmatic/server values.

TextArea invalid uses aria-errormessage, warning/helper/counter descriptions have different associations, and fluid suppresses some ordinary helper relationships. Counter announcements are delayed (one second for character mode, two for word mode). Inspect rendered relationships and actual announcements for invalid, warning, fluid and rapid edits; source attributes alone do not establish assistive-technology support.

PasswordInput defaults to masked password type, maintains visibility state, updates it when type changes, and invokes onTogglePasswordVisibility with the event. Its separate native button uses translated Show/Hide password tooltip labels and supports native button activation; do not bind reveal to Space in the text field. Disabled also disables the reveal button; readOnly is distinct. Verify the rendered accessible name and focus, autocomplete/password-manager integration, state preservation and whether visibility persists for the intended workflow. Masking is a visual affordance, not storage or transport protection. ControlledPasswordInput and fluid variants were located but not fully inspected.

For AI-generated values, expose explainability and preserve an original value so users can edit, accept or revert suggestions deliberately. An AI decorator does not implement that data workflow. Verify ordinary/error/read-only/disabled states, label and error association, keyboard/touch/IME editing, counters and paste, password toggle, async rejection, fluid/default alignment, long labels/errors, responsive/RTL/zoom and actual theme contrast. No Text input runtime/AT pass was performed.

## Slider: numeric value or bounded range

Use when users benefit from exploring a numeric range and can still enter exact values where needed. Very small discrete sets suit radios; extremely broad/precise values often suit numeric inputs; dates use DatePicker. Separate the overall allowable bounds from the user's selected lower/upper endpoints. Label the quantity and units, not only Min/Max placeholders.

- Keep input values, thumb positions, displayed/formatted amounts and submitted values synchronized. Define finite bounds, positive step, rounding precision, equal endpoints, crossing policy and how typed blank/invalid/out-of-range values behave. Explain auto-correction; do not silently coerce a meaningful value and call it successful validation.
- Standard tab order is thumb then number input; range is lower input, lower thumb, upper thumb, upper input. Give each range thumb/input a distinct persistent name and dependent min/max relationship. Placeholder text is not a persistent accessible name. Keep tab order stable as handles move. Value units/custom meanings need accessible value text as well as a visual tooltip.
- Arrow keys adjust by step; larger increments must match the actual installed implementation. [APG Slider](https://www.w3.org/WAI/ARIA/apg/patterns/slider/) expects Home/End to set bounds, rather than the Usage page's “move to range-selector headers” wording. [Multi-thumb guidance](https://www.w3.org/WAI/ARIA/apg/patterns/slider-multithumb/) requires stable thumb traversal and updated dependent bounds. Touch assistive operation needs device testing; a mouse drag or desktop keyboard pass cannot establish it.
- If numeric inputs are hidden, show the current value on focus/hover/active and preserve an accessible non-drag operation. Do not assume a tiny handle is the entire hit area. Style documents a 4px track, default 14px handle/20px active and range 16px handles, with label-01/body-compact-01 roles. Recommended 200–640px width is explicitly not built into the component; accommodate narrow/zoomed layouts and actual grip target size.
- Disabled and read-only differ in focus/readability and mutation prevention. Verify all pointer, drag/touch, thumb-key and typed-input routes. Error/warning messages must describe the affected endpoint and remain associated with it; color alone is insufficient. Preserve meaningful correction/status messages and translate them.

Selected installed `@carbon/react@1.117.0` declarations/source inspected: range uses `unstable_valueUpper`, `unstable_ariaLabelInputUpper` and `unstable_nameUpper`, not a presumed separate stable RangeSlider export. `ariaLabelInput` names the lower input/thumb; both names need the quantity/unit context. `onChange` and `onRelease` return `{ value, valueUpper }`, while `onBlur` exposes string value and handlePosition. Do not confuse change with durable backend completion or assume release covers every keyboard/edit submission path.

The runtime handle handler uses arrow delta=`step`, then multiplies by `stepMultiplier` when Shift is held; default multiplier is 4. Its declaration's `(max-min)/stepMultiplier` statement conflicts with that source, and the website's 10-unit example is not a default. Home/End are absent from this handler: preserve/report the gap against the APG contract and verify the selected component or approved adaptation rather than claiming conformance. Read-only guards exist on drag/key/input handlers; read-only thumbs are removed from ordinary tab order while number inputs remain read-only. Lower thumb has formatted aria-valuetext, while the inspected upper thumb has value/bounds/name without that text: verify semantic units on both. Selected source inspection is not runtime or assistive-technology proof.

Verify start/end/step and invalid totals, both handles/crossing, precise typing/correction, arrow/Shift/Home/End, callback counts and payloads, persistent naming/descriptions, non-drag access, touch AT, readonly/disabled, RTL direction, long/unit labels, responsive/zoom and actual focus contrast.

## Search input and application results

Search is a basic input mechanism for global, page or component scope. Make that scope explicit in its name/prompt, including multiple search landmarks on one screen. Use search when a meaningful dataset benefits from it; do not replace simple discoverable navigation with unnecessary search. Default search's visually hidden label is still required: placeholder text is not its accessible name.

- Choose deliberate submission or active filtering, including keyboard Enter and composition/IME behavior. The component does not query data, register a result route or implement suggestion navigation. Keep query, active suggestion, committed result and filter scope distinct. A Search input alone is not an accessible combobox.
- Provide pending/error/zero/matching/total results feedback and usable result navigation. Preserve the query on failure, discard stale remote responses and make clear/reset scope explicit. Clearing a query does not automatically clear structured filters. Do not move focus on every keystroke; announce useful status without flooding live regions.
- Public keyboard guidance uses Escape or an accessible clear button to clear text, with focus retained in the input. Expanded variants need trigger naming/state, hidden-input tab removal and reliable focus entry/return. Test nonempty and empty Escape within surrounding dialogs: a search key handler can consume Escape before the parent can close.
- Default heights 32/40/48px and fluid 64px use body-compact-01 input and label-01 fluid label, contextual field/border/focus roles, 16px icon glyphs and room for clear controls. Width follows context; test full queries, narrow viewports, translated labels and RTL. The style table's padding dimensions are not evidence of an actual rendered hit target.

Selected `@carbon/react@1.117.0` Search source inspected: wrapper role=search uses its label, native input defaults to type=search, `labelText` is required, and the old input `role` prop is deprecated. The website's instruction to make the containing div a button refers only to the expandable magnifier trigger, not the whole search region. Clear calls onChange with an empty target value, onClear, then focuses the input; controlled state must accept that update. Escape stops propagation and clears nonempty input, or focuses the expandable trigger when already empty. Enter submission is not implemented by this handler; wire the actual form/search action. The native clear button has type=button. Expanded state/inert input are supplied, while parent onExpand owns expansion. Verify CSS-hidden clear traversal and installed ExpandableSearch behavior separately; no complete expandable/fluid source or runtime audit is claimed.

Verify scope/name, text editing and IME, submission/filtering, clear payload and focus, Escape routing, expansion and hidden controls, suggestions/results semantics, pending/stale/error/empty states, keyboard result navigation, responsive/theme/RTL contrast. Upstream input accessibility does not prove the composed search experience.

## Form handoff

- Use an actual form for a submission task, associate every control with its name and associate help/errors with the relevant input. Buttons inside the form need deliberate types so supporting actions do not submit accidentally. Native required semantics and domain/server validation have different jobs.
- Keep required/optional treatment consistent. Mark the minority, with an instruction at the start such as All fields are required unless marked optional. The simple login convention does not justify omitting required semantics elsewhere. A visible asterisk or label suffix must have programmatic meaning.
- Default labels sit above the input; fluid labels sit inside. Persistent default helper text can be replaced by error/warning text; preserve essential instructions through that transition and keep their associations valid.
- Fluid inputs use disclosed help because they lack the usual helper-text area. This documented exception does not permit hover-only essential instructions: use the supported keyboard/touch-operable toggletip or component help contract, and expose the relevant description. Enter/Space opens an information toggletip and Escape dismisses it. Tooltip text with interactive links needs a suitable interaction pattern.
- Keep default inputs aligned to wide-grid columns, with about 32px vertical separation; fluid inputs form an attached unit with no open spacing and a 1px condensed gutter between columns. Don't hang default field labels into gutters.
- Prefer one column on mobile. Where a desktop row has two logically related fields, account for validation height as a row: a longer error on one side must not leave the other field visually detached. Avoid CSS order that changes reading/keyboard sequence.
- Input height follows the selected variant: 32/40/48px default, 64px fluid before messages. Use actual type tokens rather than copying inconsistent numbers: Form Style lists 28px with heading-03, while Data table Style lists heading-03 as 20px. Verify installed token definitions and the chosen hierarchy.
- Form Usage's read-only Coming soon row conflicts with current input-specific guidance. Check each supported control and [control-state semantics](accessibility.md#control-states); do not equate read-only with disabled or claim that every input supports a native readonly attribute.
- Apply AI styling to the parts actually generated, not a whole mixed-origin form. Saved original suggestions and explanation access remain separate from user edits and submission.

Verify native submission/Enter behavior, supporting button types, labels/instructions, required/error association, loading and duplicate prevention, failure preservation, help keyboard/touch access, multicolumn error growth, focus and actual mobile/zoom/theme behavior.

## Number input

Use a stepper for a quantity whose nearby increments are useful. A wide range alone does not require a slider: exact entry may be more important than relative adjustment. Numeric-looking identifiers such as postal/account codes need text entry preserving their representation, not arithmetic stepping.

- The documented keyboard contract is one input tab stop, direct entry and Up/Down adjustment; pointer +/- controls are outside the tab sequence. Verify installed and mobile behavior rather than adding redundant key handlers.
- Give a visible label and explain units, bounds and step before entry; associate helper/error text. Validate typed values as well as steps, including min/max, decimal precision, empty state and out-of-step values. Native default step is 1; its base depends on min/value, so decimal limits alone do not establish the increment.
- Choose a task-valid default rather than copying 1 globally. Public Carbon advises an initial value, but a fabricated value is inappropriate for an unknown quantity the user must supply; document that task-specific deviation and allow correction/clear behavior deliberately.
- Native number input represents floating-point values, not simply digit-only strings. Accessibility prose says only numerals can be entered while its error illustration includes `e`. Test signs, decimals, exponents, localized entry and transient invalid/empty input; do not claim a digit-only guarantee or prematurely coerce away correction state.
- Default heights are 32/40/48px; fluid is 64px before validation growth. Preserve contextual roles, readable read-only values and error/warning distinctions. Public disabled-state prose overstates screen-reader invisibility; verify semantics rather than removing necessary information.
- Manual override of an AI-suggested number removes AI styling; deliberate revert restores the suggestion/provenance. Reuse [AI explainability](ai-explainability.md).

Verify typing and arrow/pointer changes, boundaries/step bases, locale/decimal/empty/errors, labels/help, read-only versus disabled, validation growth and exact persisted quantity. No NumberInput runtime pass has been established.

## File uploader

Choose button selection or a drop zone with equivalent file-dialog access. Dragging must not be the only way to upload. Specify allowed formats, size/count limits and whether selecting a file uploads immediately or stages it for later submission.

- Button/drop zone responds to Tab and Enter/Space. The file dialog returns focus to its invoking control. Each remove control has a name that includes the target file; x alone is ambiguous when several files are present.
- Keep section heading, useful limitations and a clear Add files/Upload label. If the page has a primary commit action, use lower upload-button emphasis. Match glyph to the actual verb rather than treating Add and Upload as synonyms.
- Selected files stack vertically and use 32/40/48px rows matched to the associated button size. The 288px example width is not a mandate that makes a narrow viewport overflow; source prose permits width adaptation to content/layout.
- Use per-file loading/completion/error state. A file chosen by the picker has not thereby reached storage. Report success only when the actual operation succeeds; implement upload/progress/cancel/retry according to the backend contract rather than assuming the Carbon component performs it.
- Keep failed files identifiable with useful per-file errors and a retry/remove route. Use an inline notification for uploader-wide failure, while preserving unaffected successful files. Expose error/status information to assistive technology; color and spinner alone are insufficient.
- Long names can truncate visually, but preserve exact identity and full-content access through keyboard/touch as needed. Distinguish similar names before a destructive removal, and move focus predictably after deleting the currently focused row.
- The documented single-file drop-zone pattern hides the drop zone after success; removing that file restores a replacement route. Hiding/replacing the focused uploader needs deliberate focus handling. Multiple-file mode keeps the drop zone available and appends rows.
- Public guidance avoids multiple uploads in a modal because of vertically stacked rows. Treat container fit and focus/scroll recovery explicitly; if multiple files need room, use an appropriate page/panel flow instead of forcing them into an inadequate dialog.
- File acceptance hints are not authoritative validation. Apply actual size/type/count and domain checks at the appropriate trust boundary, with honest errors. Do not transmit private files to unrelated tooling during verification; use synthetic fixtures.

Verify keyboard dialog access, cancellation/focus return, allowed and rejected files, duplicate/oversized selections, partial failures, removal names/focus, retry/cancel, exact filenames, progress announcements, single-file replacement and responsive/themed layout. Do not generalize icon-only-danger-button prohibition to removing a pending uploader item without considering its specific documented accessible x action and actual consequences.
