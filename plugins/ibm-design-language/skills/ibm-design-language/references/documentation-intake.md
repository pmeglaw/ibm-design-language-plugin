# Carbon documentation intake and conflict resolution

Use when researching a component or translating design into code. The 2026-09-29 audit retrieved the public Carbon website's 317 MDX source files and navigation at commit `d8783ad2ae3b5e59c58f58311491f8a2c4e62631`. Retrieval/indexing is separate from reading all content, viewing examples, checking exports, and running an application. The exhaustive review remains in progress; no general mastery claim is supported.

## Four component contracts

| Surface | Extract for the requested task | Insufficient evidence |
|---|---|---|
| Usage | Selection, variants, anatomy, meaningful states, content and interaction behavior | A list of headings or image captions |
| Style | State-specific semantic paint, type roles, dimensions, spacing and sizing tables | Generic grid/tokens knowledge without component exceptions |
| Code | Correct framework/package/version, imports, exports, props, events, state ownership and feature flags | A demo iframe, another framework's implementation or future preview |
| Accessibility | Names, roles/states, keyboard paths, focus movement/return, announcements and component-specific exceptions | A library badge or a screenshot |

Read applicable variants and tables, not just the first tab. Follow framework documentation/Storybook links from Code. Resolve injected content: component accessibility-status widgets, the action-label glossary, palette widgets and chart demos have separate data sources. A source MDX snapshot alone can omit their rendered contents. Inspect rendered examples when visual details matter. Preserve the difference between stable, preview, design-only, deprecated and access-limited material.

Record a small implementation receipt: `source and date | installed package/version | selected variant/flags | product semantic roles | relevant state/interaction contract | checks and unresolved limits`. Do not turn this into bureaucracy for a simple factual answer.

## Resolve source conflicts before copying

The [developers accessibility page](https://carbondesignsystem.com/guidelines/accessibility/developers/) contains examples that need correction against current platform standards:

- `role="tabgroup"` is not the tabs pattern. Use supported Carbon tabs or the [APG tablist/tab/tabpanel relationships and keyboard contract](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/).
- A table's obsolete `summary` attribute is not the preferred description mechanism. Use a caption, associated description when needed, and proper header relationships according to the [HTML table model](https://html.spec.whatwg.org/multipage/tables.html#the-table-element).
- Assigning `onfocus = someFunction()` invokes the function immediately. Register a callback appropriate to the framework/event API. Pair pointer-only information with keyboard access without duplicating activation.
- Redundant native landmark/button roles are not a reason to wrap everything in generic ARIA. Native semantics come first; custom widgets require a complete contract.

Component-specific guidance can be newer than a general overview: the AI guideline's future-tense rename/stability statement conflicts with the AI label Usage page's stable status. Record that conflict; verify installed exports before implementation. Likewise, the feature-flags overview describes future v12 defaults but does not prove the target application is already on v12 or uses those flags. Design-kit toggles and runtime flags must agree.

## Learning and evaluation evidence

Documentation knowledge is evaluated with concrete decisions under constraints. Runtime integration, visual craft, keyboard/focus, assistive technology, and recovery need practical checks. Keep known author-written probes separate from held-out cases and retain failed executions. Hashes prove delivered inputs, not exclusive reliance or evaluator judgment. Passing text probes or synthetic evaluator tests does not certify WCAG compliance, broad design improvement or senior-engineer mastery.


## Design-kit intake and handoff (source reviewed 29 September 2026)

The pinned [Figma kit page](https://carbondesignsystem.com/designing/kits/figma/) separates IBM-internal SSO/library access from external Community-file duplication and workspace library publication. Select the workflow appropriate to the actual account. Reading this page does not prove library access, current Figma menu locations, licensing entitlements, publication permission or the contents of the linked files. Do not request IBM team membership merely because the kit is not visible; the documented internal workflow says organizational access is automatic after SSO.

The described v11 system library has White, Gray10, Gray90 and Gray100 themes; optional Type Sets, Color, UI Icon and Pictogram libraries serve different asset roles. Insert component instances from Assets and configure their component-set properties. Record the exact library/version, variant, size, theme, layer, interaction state and runtime feature flags in handoff. Figma variants do not themselves implement keyboard interaction, naming, state transitions, validation or database behavior. Keep approved brand aliases and application-specific design decisions authoritative.

The Screens asset describes five 2x-grid breakpoints and a 16-column grid with/without a left-panel influencer. That is a kit description, not permission to use 16 columns at every runtime breakpoint. Reconcile with actual Grid/Column APIs and content width after the shell/influencers. Apply semantic color variables to fills, strokes and text, and the relevant Type Sets text style; verify the effective theme/layer and fonts. Do not confuse a palette library with a component's semantic theme. A design screenshot alone cannot establish loaded web fonts, responsive overflow or accessible contrast.

The [Sketch kit page](https://carbondesignsystem.com/designing/kits/sketch/) explicitly says its libraries are no longer maintained and recommends Figma. Treat later paragraphs promising regular kit updates and the March2022 v10→v11 migration instructions as historical; do not infer current releases or prescribe Sketch installation from them. Keep library symbols connected and prefer supported overrides when working with authorized legacy documents, while verifying the actual kit and runtime versions independently.

The Sketch grid arithmetic example is internally inconsistent: it lists 288px total margins, later subtracts 272px and reports 1,056px from a 1,312px artboard. Neither subtraction produces that width. Calculate current usable width from the real panel and both margins, then choose the applicable content breakpoint; do not copy the example's number into code. The old mobile, visualization, accessibility and Gatsby kit links were read as references, but their actual files and artwork were not inspected. Kit-file operations, publishing, rendering and design-to-code parity remain untested in this audit.
## Contribution readiness and documentation (source reviewed 29 September 2026)

The [contribution overview](https://carbondesignsystem.com/contributing/get-started/overview/), [design](https://carbondesignsystem.com/contributing/get-started/design/), [code](https://carbondesignsystem.com/contributing/get-started/code/), [checklist](https://carbondesignsystem.com/contributing/component-checklist/) and [templates](https://carbondesignsystem.com/contributing/documentation/) describe an upstream contribution workflow. Coordinate scope and ownership before duplicating an assigned issue; distinguish an exploratory Labs asset from a stable core component. Check the target repository's own CONTRIBUTING instructions and supported tools. Historical gallery/champion dates, office hours, internal kit files and videos do not establish current availability. These pages' commit/PR/publishing instructions do not authorize those actions for the user's project.

The checklist requires design, code, documentation and kit readiness for Stable. Discovery/Delivery preview assets can lack stable requirements and change. A demo, package export, release label or automated badge alone cannot establish that every requirement is met. For a contribution, connect the design specification to the implementation and kit: semantic color/type/spacing, sizes/alignment, main and interaction states, responsive/overflow behavior and keyboard/focus accessibility. Check actual font loading, content variation, theme/layer, RTL and zoom in the product. The checklist's simplified text-contrast rule is not a replacement for current WCAG criteria, exceptions or measured effective colors.

Preserve consumer experience in API design: logical composition, typed/exported interfaces, configurable user-facing strings and compatibility with the target framework/runtime. Use supported tokens and explain necessary structural dimensions rather than inventing new brand colors or treating every measurement as a spacing step. Build documented behaviors as well as appearance. Break changes through deprecation and a feasible migration; an upstream Carbon contribution may need a codemod in @carbon/upgrade. A consumer application does not acquire an obligation to publish a Carbon codemod or support every historical React version.

Upstream readiness includes default/playground stories, long-form documentation, unit coverage (the checklist specifies 80% functions/lines/statements), visual regressions, automated accessibility and manual JAWS/VoiceOver/NVDA checks. Apply the project's approved test tools and required gates to consumer work; do not replace its runner with Jest or add Percy/Storybook dependencies merely because the upstream checklist names them. Exercise complex states and widths beyond the default story. Retain manual assistive-technology checks as untested when not run; source review and automated scans cannot stand in for them. Internal Figma best-practice files and actual kit parity remain outside this source review.

### Write documentation that supports implementation

Use the four contracts above as complementary deliverables. In Usage, identify the task, appropriate alternatives, anatomy and optional parts; distinguish major variants, visual styles and minor modifiers. For multiple variants, put genuinely shared behavior once and map every variant-table entry to its detailed section. Explain state transitions, initial state, actionable area, pointer and keyboard operation, validation, loading, responsiveness and overflow as applicable. Separate alignment within a component from placement in the page/grid. Content guidance should explain names, labels, helper/error text and overflow without silently truncating essential information.

In Style, document enabled and interaction states using element/property/token tables; place state first in interactive tables. Include type size/weight/token, structure and spacing dimensions, size names/heights, contextual layer notes and corresponding annotated images. Share tables only when variants actually share values. Link size-selection advice back to Usage. Optional AI guidance must describe the affected content, explainability and revert behavior, plus only the styling differences; current API terminology and exact installed component support govern implementation.

In Code, give verified imports and runnable common-use examples, then explain additional behavior with actual prop types/defaults and state ownership. Carbon's template alphabetizes prop tables and uses dashes for inapplicable entries; a placeholder table is not API evidence. In Accessibility, separate what the library supplies from product-owned names, heading levels, meaningful order and focus/announcement requirements. Illustrate keyboard navigation and activation in prose as well as diagrams, and describe custom-composition obligations. Status widgets report their specific upstream tests, not application conformance.

Patterns document a user objective and flow across components, with contextual anatomy, behavior, alternatives, visual guidance and accessibility. Share universal behavior and explain each variant's differences and rationale. Use annotated layouts, flows or prototypes appropriate to the problem. Choose maintained, authorized kit assets; the templates' Sketch-file request does not override the current kit page's unmaintained notice. Write concise, direct, sentence-case guidance, explain related choices and retain useful references. Review rendered navigation, anchors, code fences and assets before publication.

## Ecosystem, releases and support (source reviewed 29 September 2026)

Carbon v11 maps to @carbon/react1.x and Elements11.x, not @carbon/react11.x. Inspect the actual package graph, peer requirements and flags; a latest website footer or historical release table is not an installed version. The release page's cadence and roadmap are descriptions, not a guaranteed delivery date. [Deprecations](https://carbondesignsystem.com/deprecations/) records v10/legacy package support ending30 September2024 and carbon-icons support ending31 March2022. Date those facts to the reviewed source; verify current package/release state before advising an upgrade. Proposed v12 support and the page's then-current React19.2 reference do not establish today's latest release or authorize a migration.

The [ecosystem](https://carbondesignsystem.com/all-about-carbon/the-carbon-ecosystem/) separates universal core assets from community/domain offerings, IBM.com, product, employee, Salesforce and conversational resources. They can have different maintainers, support, access and implementation contracts. Do not treat an internal-only link as read, or assume React examples apply to LWC/native apps. Preserve the approved product brand while selecting appropriate universal patterns; IBM-specific branding and restricted guidance do not become automatic requirements for external products.

The [FAQ](https://carbondesignsystem.com/help/faq/) names current mainstream browser families and differentiates official React/Web Components from community frameworks. Check versions and actual target browsers when choosing APIs; that list is not proof of cross-browser success. Preview/feature-flag/community assets remain distinct. The [contact page](https://carbondesignsystem.com/help/contact-us/) routes issues by design kit, icons, website, components/elements, charts and framework, with internal Slack versus public support channels. Prepare a minimal reproduction with package/version, selected flags, observed/expected behavior and evidence; remove private application data. Check existing reports before proposing a new issue. Never promise the FAQ's aspirational response timeframe, contact a maintainer, open an issue or send an email without task authorization.

The [certificate page](https://carbondesignsystem.com/help/certificate-of-originality/) is historical IBM material/version identification; it does not prove a project's licensing compliance or permit using every linked brand asset. [Meetups](https://carbondesignsystem.com/whats-happening/meetups/) describes IBM access and review resources, not guaranteed current schedules. News and home pages inject MediumPosts from a Gatsby build-time feed, sort by date and filter selected design-ibm/carbondesign links before limiting to9 or3 cards. The widget and homepage wrapper source were read; the current feed, imagery, external articles, videos and event operations were not inspected. Treat reading-list recommendations as context, not normative implementation requirements.

### Telemetry evidence boundary

The reviewed FAQ describes optional install-time telemetry for eligible IBM/Carbon origins on CI outside PRs and says the data is not anonymous; it documents CARBON_TELEMETRY_DISABLED=1 as opt-out. Installed @carbon/react1.117.0 declares a postinstall command invoking ibmtelemetry with telemetry.yml. Its selected config keys include JSX attribute-name/string-value allowlists, npm dependency collection and JS fields. This manifest/config check does not prove execution, collected payload, effective eligibility or transmission, and the FAQ's general statement about serializable prop values is not an exhaustive implementation specification. Inspect the versioned collector and project policy when telemetry matters. Do not execute an install or change settings merely to test collection, or send private office data in a support reproduction.

## Migrating from v10 to v11 (source reviewed 29 September 2026)

The [overview](https://carbondesignsystem.com/migrating/guide/overview/), [designer guide](https://carbondesignsystem.com/migrating/guide/design/), [developer guide](https://carbondesignsystem.com/migrating/guide/develop/) and [FAQ](https://carbondesignsystem.com/migrating/faq/) concern this specific historical transition. Their no-brand-redesign claim does not mean DOM, props, states, tokens, kit assets and accessibility are unchanged. Use current target APIs and owner decisions, not a blanket visual guarantee or an effort estimate based on the page's agentic-tooling optimism. Confirm the source/target versions, actual consumers and compatibility strategy before an authorized migration; preserve a reversible baseline and test affected behavior and visuals before declaring it done.

React migration consolidates legacy styles/components/icons into @carbon/react; styles-only authors use @carbon/styles, while other frameworks require their own compatibility guidance. Avoid deleting a direct dependency still used elsewhere or silently installing latest versions. Dart Sass replaces node-sass; configure actual resolver/load paths and verify modules in the installed package. Use @use with explicit namespaces where collisions matter. Historical advice that @import remains usable is not a reason to introduce deprecated Sass imports into new work. Compile times and export-count reductions on the page are release claims, not measurements of the user's project.

Codemod order matters: small-to-size-prop precedes size-prop-update; icons-react-size-prop precedes update-carbon-icons-react-import-to-carbon-react. The import migration uses update-carbon-components-react-import-to-scoped. Verify the chosen @carbon/upgrade release, supported arguments and transformations in an isolated authorized workspace before using --write; inspect warnings and review the diff. Codemods do not prove completeness. Manually check ref-preserving icon adapters, computed imports, removed icon alternatives, snapshots and changed className placement. Icon glyph sizes become a size prop on a single exported component. Choose replacements by meaning, not merely a similar name. Do not blanket-replace a CSS prefix across unrelated styles; align generated CSS and component configuration.

Treat sizing tables as naming guidance, not a guarantee that every component supports all six values or defaults to md: the actual component contracts remain authoritative. v11 Tabs separates TabList/TabPanels/TabPanel and places selection on Tabs; preserve panel/index correspondence, naming and keyboard behavior. Notification actions require an appropriate actionable composition; tooltip information and interactive disclosure have different semantics. The overview incorrectly says tooltips can only contain interactive content, immediately contradicting its Toggletip explanation. Follow the reviewed Tooltip/Toggletip contracts. The designer guide's blanket definition-tooltip migration statement also requires installed API verification rather than removing DefinitionTooltip indiscriminately.

Update renamed type/color roles and layering rather than merely changing strings. Keep design-kit theme/layer/variant choices consistent with code; the historical Figma swap workflow and legacy Sketch/XD availability are not current UI/access verification. GlobalTheme context alone does not emit theme CSS or implement persistence/OS preference handling; pair actual CSS scopes, theme/layer context and application preference logic, including overlays. Removing old v10 Sass feature flags is separate from deciding whether to enable today's v11 runtime/visual flags.

Five narrow compilation probes against @carbon/react1.117.0/styles1.116.0 and Sass1.105.0 all compile, including the FAQ custom-theme recipe. However, the developer guide's granular recipe sets $use-flexbox-grid to the string 'true': it does not emit .cds--row. The installed style source compares the setting to boolean true, and the boolean probe emits that selector. Successful Sass compilation therefore does not establish the intended grid. The custom theme emits a literal rgba color for its custom token; this is different from passing a CSS-variable token through Sass rgba and is not contrast or browser-cascade proof. Placeholder font paths, brand colors and local sample-grid imports require project-specific values; our probes did not load fonts, run a migration/codemod, render layouts or execute telemetry.
