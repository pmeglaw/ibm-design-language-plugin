## Create, add and edit

[Create](https://carbondesignsystem.com/community/patterns/create-flows/) generates a new resource; Add associates an existing resource. [Edit](https://carbondesignsystem.com/community/patterns/edit-pattern/) changes an existing resource. Match the label and transaction to that distinction. Prefer inline interaction for a small contextual task, a focused dialog for a short blocking task, a panel where surrounding context matters and a larger flow for substantial work. The source's field-count thresholds,480px side panel,256/320px step navigation and proposed80px footer are community examples/heuristics, not mandatory dimensions or proof of an available API. Test actual narrow/long-content behavior; current core Modal supports scrolling, so the old no-scrolling rule does not prohibit an appropriate modal.

Keep existing creation/edit conventions where they support the user's task. Multistep Next/Back/Create state, validation, dirty changes, staged values and server submission belong to the application. Preserve values on Back and recoverable failure; don't mark a step complete merely because its indicator is selected. The source's show-all toggle changes presentation from steps to anchors: preserve shared values and explicitly handle any real destructive consequence rather than silently discarding hidden fields. Do not add this mode by default. Distinguish required-field prerequisites from a validated submission; disabling a button alone neither explains errors nor enforces server rules.

Application integration must define cancellation, navigation-away handling, pending duplication and race handling. A source Cancel label or hidden close icon does not implement rollback, browser-navigation protection, focus restoration or Escape behavior. Confirm loss when actual unsaved work would be lost; don't add an unconditional modal to every navigation. Low-impact edits usually need no extra warning. For consequential changes, show the actual resource and consequences with a useful summary; don't assert irreversibility or stack two confirmations merely because the community example does. Non-editable information should remain perceivable; readonly or static presentation can be more appropriate than the edit page's blanket disabled-field suggestion. Report saved/created only after the operation succeeds, retain meaningful errors and move focus according to the actual composition/task.

## Remove and delete

[Remove](https://carbondesignsystem.com/community/patterns/remove-pattern/) separates impact and reversibility. Preserve the clearer core [action distinctions](patterns.md): Remove can unlink/move an association, Delete destroys the resource. The community wording that deletion is a kind of removal does not justify interchangeable labels or broader backend deletion. Explain affected identity, dependent consequences and actual undo capability. High-impact irreversible deletion may need typed resource-name confirmation; smaller irreversible actions can use a clear confirmation, while reversible low-impact actions may use undo without a dialog. Follow owner-approved safety rules where stricter.

Typed confirmation requires an actual identity-comparison policy and server authorization; it is not access control. Never claim 'cannot be undone' for a reversible action or promise undo that is unavailable. The page's passive success dialog for a request in progress conflates accepted and completed: distinguish requested, processing, failed and completed. A notification does not implement the mutation or prove completion. Ensure returning focus after removal reaches a surviving meaningful control, and retain error/retry context instead of deleting the row optimistically without a recovery contract.

## Import and export

[Import](https://carbondesignsystem.com/community/patterns/import-pattern/) combines local browse/drag-and-drop with optional URL import and metadata. URL import is conditional on existing product support; do not add a remote-fetch service just because the example offers one. Use actual allowed types/count/size rules, accessible browse and named remove controls, validation and a clear review/commit boundary. Selected, uploaded, parsed and imported are different states. Neither accept filters nor a loaded-file icon establish server validation or successful data mutation. Preserve the product's atomicity, duplicate and overwrite rules; don't infer them from FileUploader. Single/multiple-file and maximum-capacity focus sequences are illustrative: verify actual keyboard controls, announce changes and recover focus when disabling/removing an element. Initial dialog focus depends on content/task, rather than always moving to the drop zone.

[Export](https://carbondesignsystem.com/community/patterns/export-pattern/) can change format; Download transfers an existing resource. Decide whether naming/format options justify a dialog or whether a direct action suffices. Offer an informative default filename and allowed formats with a meaningful default. The two-to-five radio-choice example is a heuristic; maintain native group naming/selection and application validation. Keep the requested format, MIME type and extension consistent instead of blindly hiding or trusting a user-editable extension. Respect authorized data scope and destination.

The source's claim that Download always opens a location panel is not portable. [MDN download behavior](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/a#download) depends on browser/settings and may prompt, save automatically or open the file. [showSaveFilePicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showSaveFilePicker) has limited availability, requires a secure context and transient user activation; picker cancellation is possible. Don't invent a guaranteed Save dialog or equate initiating an anchor download with confirmed disk persistence. If a supported picker is used, selecting a handle is not itself the completed write. Separate export preparation, request start, cancellation, failure and verifiable completion in copy. Preserve inputs on failure and follow actual modal focus/return behavior instead of treating the old Export-first/Close-icon sequences as universal.

## API-key generation

[API-key guidance](https://carbondesignsystem.com/community/patterns/generate-an-api-key/) asks for clear purpose, permissions, destination and retrieval expectations. Explain actual scope/resources before generation; optional name and management-page placement should fit existing IA. A 'general access' example does not make broad permissions a safe default. Enforce real authorization and scope on the server; controls and masking are presentation. Present the returned key only when generation succeeds; handle pending/retry without accidental duplicate issuance. Editing metadata/scope is distinct from editing a secret's contents or rotating/revoking it.

State whether the secret is recoverable, where, and whether it will be shown only once, using the actual service contract. Provide copy/reveal/download only when authorized and supported. Encoding is not encryption or protection. Copy success needs the actual clipboard result; do not expose secrets in logs, test evidence, analytics, URLs or support examples. Use fictional placeholders for evaluation. Masking and a download link do not establish secure storage. The linked reusable component is internal and uninspected; don't import APIKeyGeneration from core based on this page. Read-only products do not acquire key-generation features from learning this pattern.

## Conversational interfaces

Reviewed [Overview](https://carbondesignsystem.com/community/patterns/chatbot/overview/), [Usage](https://carbondesignsystem.com/community/patterns/chatbot/usage/), [Content](https://carbondesignsystem.com/community/patterns/chatbot/content/) and [Flows](https://carbondesignsystem.com/community/patterns/chatbot/flows/) are community guidance. The overview's 'out of the box' wording conflicts with its Development status table: all listed items need contributions, with some designs preview/coming soon. The Sketch add-on is not proof of current Figma assets or executable components. Verify the actual supported chat package independently.

Choose chat only when natural-language, on-demand assistance improves the user's task over ordinary controls/docs. Clearly identify the bot, purpose and limits; fit tone to audience without impersonation, forced friendliness or unsolicited messages. Reflect ambiguous intent and confirm consequential actions using concrete consequences. Offer bounded structured responses and an escape from dead ends; don't assume every task should become a conversation. Preserve read-only task/product boundaries. Medical/financial examples illustrate domains, not evidence that the bot is qualified to advise in them.

Anatomy includes named launch/close controls, header, identifiable system/user messages, optional cards/structured responses and input/submit. Make essential prior messages readable: a faded treatment must not destroy contrast. Structured choice appearance must match submitted content, and input/voice options require actual supported behavior. Bottom-right placement, up to four header actions and card variants are examples, not universal mandates. Keep controls usable at small widths and logical reading order; closing, reopening and switching threads need a product-owned focus/history contract.

Multiple threads/human handoff, expanding cards and error states are marked Preview. Do not simulate a live agent or promise handoff availability. Announce actual participant/context changes and provide perceivable unread information rather than a dot alone. Critical card content stays available without expansion; long detail may use a supported full view with a return path. The source's instruction to clear message errors when connected is insufficient: reconnect does not prove delivery. Model queued/sending/sent/failed and retry by actual acknowledgment, avoiding duplicate sends and lost text. Streaming, cancellation, stale responses, transcript announcements and persistence require additional application design/testing; the source pages do not implement them.
