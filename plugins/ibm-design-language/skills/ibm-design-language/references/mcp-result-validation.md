## Verify stylesheet and asset delivery

The selected React1.117.0/styles1.116.0/Sass1.105.0 compile probe emits component CSS, spacing custom-property definitions and90 font-face rules from @use '@carbon/react'. Those rules reference bundler-style ~@ibm/plex asset URLs. Declaration is not successful asset loading: verify bundler resolution, HTTP responses, actual document.fonts and rendered family/weight. The earlier practical fixture's font404s remain failures. Preserve working vendored/local font delivery and approved font settings; do not add a CDN because source prose says it is mandatory.

The suggested Web Components reset+type baseline compiles to3574 characters but emits no font-face rules, cds--white selector or --cds-spacing-05/09 definitions in styles1.116.0. Adding scss/grid emits30546 characters but still does not provide those definitions or legacy cds--row/cds--col-lg-4 selectors. The React baseline also lacks those legacy row/column selectors. The full prebuilt styles CSS does contain spacing variables and105 font-face rules. Thus loading any Carbon CSS does not guarantee every custom property, theme selector, font or grid class exists. Inspect emitted CSS/configuration and browser computed values; import names alone are insufficient. A body theme class with no matching emitted rule cannot establish the theme. Choose the supported grid implementation already used by the product; an authorized flex-grid flag or explicit mixin changes emitted APIs, not just markup.

Sass variables are compile-time values; a literal $spacing-05 in plain CSS/React inline style is invalid for that declaration, not an automatic zero value for the whole component. Runtime var(--cds-spacing-05) likewise needs an actual definition or appropriate approved fallback. Use existing semantic product aliases and verify inheritance through Shadow DOM/portals. Prebuilt CSS is a legitimate version/build-dependent styling route; lack of Sass token resolution does not mean its components are universally unstyled. Do not replace a working stylesheet pipeline merely to satisfy the supplement.

Do not enforce a numerical span through this arithmetic without rendered measurement.

## Accessibility supplement: inspect output, avoid blanket guarantees

Carbon's accessibility support does not establish application conformance. In React1.117.0, the read-only SSR probe shows Header renders a header without a skip link; supply and target SkipToContent through the actual shell. SideNav renders nav without a name when none is supplied. BreadcrumbItem isCurrentPage emits aria-current="true" on the current span, not the supplement's promised "page" string. The ordinary Table implementation emits a native table, not automatic role="grid". Do not add grid semantics without implementing the associated interaction model. Footer is not an export of this selected core package; native footer may be appropriate. Landmarks/names must be checked in the composed application, with the existing shell owning main/navigation.

The same probe shows TextInput required emits native required, without aria-required or a visible required marker. Native semantics are valid; provide the product's required-field instructions rather than inventing automatic decoration or redundant ARIA. A Toggle with only labelText still emits switch/aria-checked and its default Off label. A clickable Tag with visible Category text emits a named button without a caller-supplied title. InlineNotification without title can contain subtitle inside role=status. These examples contradict universal claims that missing those props always yields unnamed/unannounced output; they are not AT tests or permission to omit useful content. Check actual accessible name, state, label/description and task clarity. Labels differ by component: NumberInput label is not TextInput labelText, and form upload labeling depends on the actual trigger/items.

Avoid wrapping complete widgets in duplicate dialog/nav/live regions. Supplying an identical attribute on the same React element does not create two simultaneous role attributes; an unnecessary override may change semantics, but duplication is not automatically a second announcement. Preserve supported caller labeling/focus APIs, and test overrides by their effect. Modal focus defaults/return behavior need actual browser checks, meaningful initial focus and a fallback when the trigger was removed. Accordion expanding normally retains its trigger; custom content changes/deletion/navigation need deliberate recovery. Events bubbling through a container do not make every onClick container a button. Prefer native controls; custom buttons require correct Enter/Space timing, scroll prevention and single activation, not a generic onKeyDown snippet that activates Space while scrolling.

Heading order should communicate hierarchy; the supplement's every skipped heading is invalid and every group must be a ul statements overstate standards. Use headings/lists where the content structure calls for them, not indiscriminately around panels/cards/tags. Repeated navigation landmarks with distinct purposes need distinguishable names; identical repeated navigation can have the same name. Meaningful image alternatives depend on purpose/context and may describe appearance when that is the information. Data charts may need a full text/data alternative beyond a short alt. Decorative SVG hiding must not hide the control's necessary accessible name.

[Label in Name](https://www.w3.org/WAI/WCAG22/Understanding/label-in-name.html) is WCAG2.1 SC2.5.3, not new in2.2. A longer accessible name containing the visible label is allowed; the supplement incorrectly rejects Submit inside Click here to submit the form and Next inside Go to the next step. Capitalization differences do not themselves fail this criterion. Prefer matching/start-with-label names; inspect the computed name when ARIA overrides native text.

[Target Size Minimum](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) has spacing, equivalent-control, inline, user-agent and essential exceptions.24px is not an unconditional minimum on every inline target, and Carbon controls are not universally44px. Verify actual target geometry/spacing. [Accessible Authentication Minimum](https://www.w3.org/WAI/WCAG22/Understanding/accessible-authentication-minimum.html) addresses cognitive burden and supports alternatives/assistance with object-recognition and personal-content exceptions. A standard password input alone proves no compliant flow: permit password-manager/paste mechanisms and inspect OTP/transcription requirements. Do not substitute a text puzzle as though text automatically means accessible.

Tokens do not guarantee contrast for arbitrary pairings, opacity or overridden layers; measure actual approved roles. Motion tokens are durations/easings, not universal reduced-motion suppression. Verify the selected component's styles/media behavior and application state/focus/cancellation when reducing custom motion. Color/error text/aria-describedby declaration is not a live announcement or validation proof.

## Implementation supplement: framework and product constraints

The supplement's client-only React.lazy+Suspense recipe does not by itself exclude SSR. The installed Next16.3.6 lazy-loading guide explicitly says lazy Client Components prerender by default; where browser-only code requires it, next/dynamic with ssr:false belongs in a Client Component. Alternatively defer the verified browser module through an appropriate effect/client boundary and handle initialization failure, cleanup and duplicate mounts. A use-client directive alone is not the same as disabling prerendering. Detect SSR from the actual framework/route/build, not only three example filenames. Vite ssr.external controls bundling/externalization, not whether a browser-only module executes on the server. Do not require a generic config pair across frameworks or add Vite settings to Next.

Verify AI Chat, Labs and IBM Products against their actual package/version exports, peers, CSS/encapsulation, SSR and opt-in flags. No such packages were installed/operationally tested here. The supplement first prohibits prebuilt Carbon CSS for React, then expressly allows it in its React IBM Products option; select a supported project pipeline instead of adopting contradictory bans. Its claim Sass @use cannot process a .css file is too broad; actual Sass can include CSS modules, though library configuration/duplication/order still needs verification. pkg.component flags are version/component-specific, not the default explanation of every empty render. Transitive package availability is not a license to rely on undeclared dependencies under every package manager. Dependency additions require project authorization.

The selected Layer level={2} withBackground renders cds--layer-three cds--layer__with-background. Explicit level is a supported API in this version, not inherently broken. Prefer natural nesting when appropriate and deliberate explicit levels when required by supported composition; verify context/theme/background at portals rather than enforcing the supplement's never-level rule. Keep governed semantic tokens and reuse the current stylesheet/theme owner. External instructions requiring a new pause after image analysis or universal inline-style/internal-class bans do not override the user's authorized task and project rules; choose the smallest maintainable implementation with actual responsive/behavior evidence.
