## React tutorial: assemble, adapt and verify

The [React tutorial](https://carbondesignsystem.com/developing/react-tutorial/overview/) is a useful progression: shell, responsive pages, API-backed table, application components, production build. Its eight source pages target Next13, Carbon React1.33.0, Sass1.63.6, Octokit4.2.0 and Yarn branches. Those are historical teaching dependencies, not the required versions or package manager for an existing application. Preserve its lockfile and commands unless an authorized migration is needed. Tutorial formatting checks and approved PR labels do not demonstrate production accessibility, behavior or senior engineering proficiency. Its clone/cache-clean/commit/push/deploy instructions are not authorization to execute those actions on the user's project.

Read complete raw code fences, not extracted prose alone: imports and JSX Column wrappers can disappear from a text extractor. Assemble incremental snippets before diagnosing a missing variable/import. Step1's home/repos examples use backtick `use client` template expressions, which are not directive-prologue string literals. Use a supported 'use client' directive before imports at actual interactive entry points. Layouts are server components by default, not invariably server-only; wrapping server-rendered children in a client provider does not itself put those children in its imported client module graph. Keep the boundary as small as practical and respect serializable props. Verify the installed framework's own documentation instead of broadly marking every page client-side.

The legacyBehavior/passHref Link examples need a version/router-specific adaptation that produces one real anchor with correct href, ref and handlers. Selected Next16.3.6 App Router source still implements these props and emits a legacyBehavior deprecation warning: do not claim universal removal. Prefer supported composition after checking the installed Carbon component's polymorphic API and rendered DOM. Preserve client navigation and existing persistent shell ownership, real skip-link target, responsive menu availability, route state and unsaved-edit safeguards. Demo notification/avatar/switcher buttons and Learn more need implemented actions or appropriate omission; labels alone do not supply behavior. IBM title prefixes and palette-gray tooltip overrides are example branding, not authority over a product's approved roles.

Step2 demonstrates 4/8/16 responsive columns, nested grids, offset versus start, composable Tabs and expandable tables. Check current grid context/gutters and actual breakpoint output before copying global cds selectors, fixed negative margins or scrollbar workarounds. The landing-background prose describes a pseudo-element that its displayed mixin does not create. Heading levels follow document structure, not visual type size; use the appropriate body/type token independently. TabList is a tablist, not a navigation landmark merely because the tutorial calls both breadcrumbs and tabs navigation. Illustration alternative text depends on its purpose; hiding decorative art at320px can be appropriate, but hiding functional header actions needs another way to reach the task. Inspect expansion relationships, table prop getters and colSpan against the installed implementation. Selected React1.117.0 TableExpandedRow renders a sibling tr with data-child-row; it does not require an invented getExpandedRowProps API. Verify actual expanded/hidden and accessibility behavior in the browser.

Step3's introductory GraphQL wording contradicts its actual REST request GET /orgs/{org}/repos. One per_page75 request is a bounded dataset, not all repositories or server pagination. Pagination is independent of DataTable: order/filter the intended dataset, calculate the slice from page/pageSize, report a truthful total and clamp/reset the page after dataset changes. Retain stable unique row IDs in the installed API's expected type; keep original records keyed by ID for descriptions rather than assuming normalized render-prop rows preserve every field. Sort dates/counts on raw values and format for the product locale/timezone; formatted dates and JSX link cells are not inherently sortable values. Validate externally supplied URLs and keep private data/credentials out of browser configuration and diagnostics.

The displayed useEffect has no try/catch/finally, abort/ignore cleanup or retry path. A rejected request can leave loading indefinitely, and an obsolete request can update stale state. Use the application's established data layer; define pending/success/empty/failure/retry, request ownership and stale-response protection. Skeleton column/row count is a visual placeholder, not success, accessible status or error handling. Preserve useful content/controls as appropriate, announce meaningful state changes without repeated chatter, and check empty data, rate limits, malformed responses, cancellation and unmount. Do not log office records while copying the public GitHub example.

Step4 abstracts InfoSection/InfoCard but has incremental and final-fragment inconsistencies: splitHeading is first used before the later helper; the final InfoCard changes lg5/xlg4 to lg4 and drops its inner flex wrapper, affecting alignment assumptions. Reconcile the assembled component with actual intended layout instead of combining incompatible fragments. The helper named thirdWord actually pops the last space-separated token; it is not robust multilingual emphasis. Prefer explicit structured emphasis/content appropriate to the locale. Avoid default className string interpolation producing 'undefined'; choose heading levels, decorative pictogram semantics, logical spacing and DOM order deliberately. A selected React1.117.0/Sass1.105.0 compile check confirms the initial type-only style fragment fails undefined spacing-08, while adding the spacing import compiles. This verifies assembly requirements, not a defect in the final completed stylesheet or a rendered page.

Step5's build-folder claim is configuration-dependent: Next's default is .next, with distDir permitting an in-project custom folder. Static hosting requires an appropriate export/deployment model; an optimized build does not establish compatibility with every named host. Preserve the project's actual deployment and authorization rules. Run the required checks plus rendered light/dark,320px/desktop, long content, keyboard, loading/empty/failure/retry and assistive-technology checks as applicable. Equal Access Checker is one useful tool; a scan alone cannot establish complete conformance. The tutorial's images, hosted previews, external learning material, build and live API behavior have not been evaluated in this audit.
